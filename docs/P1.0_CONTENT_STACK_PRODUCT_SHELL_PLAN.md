# P1.0 — Content Stack & Product Shell Plan

## 1. Purpose

P0 proved the Paper Engine. P1 turns the prototype into the first real journal creator by adding content above paper and then wrapping it in a coherent mobile product shell.

The governing product sequence remains:

> choose paper → lay / layer / erase paper → add visual content → write / handwrite → draw → manage pages

P1 must preserve the P0 properties that already passed acceptance:

- renderer-independent artwork data
- logical page coordinates
- local-first editing
- two-finger viewport gestures
- one committed gesture = one History operation where applicable
- no high-frequency pointermove document writes
- persistence after committed operations
- no dependency on Konva JSON

## 2. P1 scope

P1 includes:

- unified PageDocument
- generic Content Stack
- selection / transform foundation
- Ink
- Image
- Text
- multi-page journal
- mobile editor shell
- P1 QA / acceptance

P1 excludes:

- VideoElement
- accounts
- cloud sync
- collaboration
- creator center
- marketplace / billing
- R2 remote asset storage
- final production asset catalog

These can be pulled forward only through a deliberate scope change.

## 3. Architecture decision: unify the document before features

The current P0 persisted document is paper-specific. P1 must not allow each content feature to maintain separate top-level state.

Target relationship:

```text
PageDocument
├── page metadata
├── paperLayers[]
└── elements[]
    ├── InkElement
    ├── ImageElement
    └── TextElement
```

All persistent artwork lives in Page Logical Coordinates.

Runtime objects remain separate:

```text
Persisted document
≠
Konva nodes
≠
HTMLImageElement
≠
Canvas caches
≠
Object URLs
≠
DOM input state
```

## 4. P1.1 must come before Ink / Image / Text

P1.1 establishes:

- `ContentElement` discriminated union
- common element identity
- common transform
- array-order z-order
- Select mode
- selected element
- hit testing boundary
- transformer boundary
- element Commands
- PageDocument persistence migration
- content renderer boundary

Without this foundation, Image/Text/Ink would duplicate selection, transforms, History, and persistence logic.

## 5. Element ordering

P1 freezes this rule:

> `elements[]` array order is bottom → top content z-order.

Do not persist a second independently mutable `zIndex` unless a future performance requirement proves it necessary.

Paper remains below every ContentElement.

Reordering content changes array order through a Command.

## 6. Common transform

Every transformable content element uses Page Logical Coordinates.

Baseline:

```ts
interface ElementTransform {
  x: number;
  y: number;
  rotation: number;
  scaleX: number;
  scaleY: number;
}
```

Intrinsic width/height remain element-specific.

Pointer-move transforms use mutable renderer interaction state and commit one Transform command at gesture end.

## 7. Selection semantics

P1 selection baseline:

- Select mode is explicit.
- Tap topmost visible content element → select it.
- Tap empty page → clear selection.
- Paper is not selected through the Content Stack selection mechanism.
- One element selected at a time in P1.
- Drag selected element → translate.
- transformer handles → scale / rotate.
- two fingers always remain viewport zoom/pan and must cancel uncommitted element manipulation.
- multi-select is deferred.

## 8. Ink strategy

Handwriting and Drawing are separate user-facing modes but share one engine.

P1.2 baseline:

- vector committed strokes
- mutable active stroke preview
- color
- width
- opacity
- no document mutation on pointermove
- Ink Eraser is separate from Paper Eraser

Ink erasing is **not** paper-style single-layer locking. It should erase intersected ink according to Ink semantics while never touching Paper Layers, Images, or Text.

Advanced pressure curves / calligraphy simulation are deferred unless required for acceptable handwriting feel.

## 9. Image strategy

P1.3 introduces binary local assets.

Document:

```text
ImageElement
→ assetId
```

Storage:

```text
IndexedDB asset store
assetId → Blob + metadata
```

Runtime:

```text
assetId
→ Blob
→ object URL / decoded image
→ renderer cache
```

Never persist:

- Base64 Data URL in PageDocument
- HTMLImageElement
- object URL

P1 image baseline:

- import
- move
- scale
- rotate
- crop
- replace
- delete
- reload recovery

## 10. Text strategy

Text input must use DOM editing for reliable IME.

Flow:

```text
select/add TextElement
↓
DOM textarea/input overlay
↓
composition events / IME
↓
commit text command
↓
Canvas/Konva display
```

Required P1 IME acceptance:

- English
- Japanese
- Korean
- Traditional Chinese

Simplified Chinese may work technically but remains outside the current product locale scope.

P1 does not require per-character rich text spans.

## 11. Multi-page strategy

P1.5 introduces a journal-level document above pages.

Conceptual boundary:

```ts
interface JournalDocument {
  schemaVersion: number;
  id: string;
  title: string;
  pageIds: string[];
  createdAt: string;
  updatedAt: string;
}
```

Individual pages stay independently serializable.

This avoids rewriting one giant journal blob after every stroke.

Page thumbnails are runtime/generated derivatives, not canonical artwork.

## 12. Product Shell strategy

The current P0 EditorShell is development-oriented.

P1.6 should evolve toward:

- page canvas as primary surface
- compact top status/actions
- mobile bottom tool navigation
- contextual bottom sheets for resources/settings
- clear active tool / active selection state
- safe-area support
- IME/keyboard-aware layout
- no red-dot/task-growth mechanics
- no forced login

Do not mix final marketing/home/discovery surfaces into the editor milestone.

## 13. Persistence and migration

P1.1 must migrate existing P0 local documents without data loss.

Required migration property:

```text
P0 paper document
↓
P1 unified PageDocument
↓
same paper layers visually and logically intact
```

Migration must be versioned and testable.

Undo / Redo stacks remain session-local unless a later explicit decision changes that.

## 14. Cloud boundary

P1 remains local-first.

Cloudflare Pages continues as static deployment and QA distribution.

Do not add Workers/D1/R2 merely because Cloudflare is already configured.

Trigger backend work only when one of these becomes real scope:

- remote binary asset ownership
- login/account identity
- cross-device sync
- creator uploads
- marketplace
- entitlements

- IndexedDB binary asset migrations
- crop implementation

Codex must not redesign frozen product rules.

## 16. Design Engineering Review gate

Reference source: `emilkowalski/skills`.

Recommended skills:

- `emil-design-eng`
- `apple-design`
- `prototype`
- `find-animation-opportunities`
- `review-animations`
- `improve-animations`
- `pick-ui-library`

Use them primarily in P1.6/P1.7.

Review order:

```text
product behavior frozen
→ functional implementation
→ functional QA
→ design engineering review
→ polish changes
→ device QA
```

Design polish may alter easing, durations, press feedback, layout details, hierarchy, or component choice.

It may **not** silently alter:

- gesture ownership
- paper eraser locking
- document schema
- local-first persistence guarantees
- accessibility
- performance budgets

## 17. P1 acceptance definition

P1 is not accepted until a real user can:

1. open a journal
2. create/modify the paper base
3. add an image
4. add text with target IMEs
5. handwrite/draw
6. move/scale/rotate content
7. create another page
8. switch pages
9. reload without losing work

And the flow passes:

- Desktop Chrome
- iPhone Safari
- standalone Android Chrome
- GitHub Actions
- persistence migration
- representative stress scene

## 18. Immediate next milestone

`P1.1 — Unified PageDocument + Content Stack Foundation`

P1.1 should be architecture-heavy and visually modest. The goal is to create the shared foundation correctly before feature volume increases.
