# P0.9 — Mobile QA / P0 Acceptance Plan

## Goal

Close the P0 Paper Engine milestone with evidence from a normal build environment and real browsers/devices. P0.9 does not add new paper-product behavior unless a QA defect requires a fix.

The frozen product acceptance source remains `docs/baseline/P0_ACCEPTANCE_CHECKLIST.md`. This document turns that checklist into the executed QA sequence.

## QA entry points

Normal editor:

```text
/
```

P0.9 browser/device QA harness:

```text
/?qa=1
```

The QA harness is gated by the query parameter and is not rendered during normal product use.

It provides:

- viewport CSS size and device pixel ratio
- touch-point capability
- document layer / mask-stroke counts
- renderer hydration count
- History depth
- current persistence state
- real IndexedDB write → read → delete round-trip
- persisted-document encode/decode round-trip
- a `+5 full layers` stress helper
- a compact manual device checklist
- copyable QA report text

The 5-layer helper creates five normal, undoable PaperLayers. It uses real PaperRuntimeAssets and full-page vector masks; it is not a renderer-only fake.

## Stage A — Repository / CI preflight

After the P0.9 patch is uploaded to `main`:

1. GitHub Actions `P0 validation` must start automatically.
2. The workflow runs Node 22.
3. It runs `npm install` in a normal public npm environment.
4. It runs:
   - `npm run papers:validate`
   - `npm run qa:p0:contracts`
   - `npm run typecheck`
   - `npm run build`
5. The workflow must finish green before final P0 acceptance.

This closes the build-verification gap caused by the generation environment's npm mirror.

## Stage B — Desktop Chrome

Open the deployed preview with `?qa=1`.

1. Run `Run self-check`.
2. Confirm automatic checks have no FAIL result.
3. Lay at least three different papers in different regions.
4. Create at least five PaperLayers, either manually or with `+5 full layers`.
5. Erase through the top paper and verify the same gesture never continues into the next layer.
6. Undo at least five operations and Redo the same five operations.
7. Fill the current paper and Undo / Redo.
8. Replace the top paper and confirm the mask shape is unchanged.
9. Zoom and pan, then lay and erase; coordinates must remain aligned with the page.
10. Wait for `Saved locally`, reload, and confirm the exact artwork returns.
11. Close the tab, reopen the preview, and confirm the local draft returns.
12. Switch through `en`, `ja-JP`, `ko-KR`, and `zh-Hant` and check that the product controls remain usable.

## Stage C — iPhone Safari

Use normal Safari browsing first. Private Browsing is a separate fallback test and must not be treated as equivalent storage behavior.

1. Open the HTTPS preview with `?qa=1`.
2. Run self-check and save/copy the report.
3. Confirm default page Fit and Retina sharpness.
4. Lay paper with one finger.
5. Start laying, add a second finger, and verify the uncommitted stroke is cancelled before pinch/pan.
6. Pinch between Fit and the maximum useful zoom; use two fingers to pan.
7. After pinch/pan, lift all fingers and start a fresh single-finger stroke; coordinates must be correct.
8. Test top-visible erasing and gesture locking across at least three full-page layers.
9. Run Undo / Redo from the HUD.
10. Wait for local save, reload, and verify restoration.
11. Background Safari / return to Safari and verify pending save is not lost in ordinary use.
12. Repeat in Japanese and Korean to check narrow mobile control layout.

Private Browsing check:

- If IndexedDB is unavailable or restricted, the editor must remain usable and show a persistence warning rather than a white screen.

## Stage D — Android Chrome

1. Open the same HTTPS preview with `?qa=1`.
2. Run self-check and save/copy the report.
3. Repeat single-finger lay, two-finger zoom/pan, and gesture-cancellation tests.
4. Test eraser target locking through multiple full-page layers.
5. Test five Undo / five Redo operations.
6. Test Fill / Replace.
7. Wait for local save, reload, and verify restoration.
8. Background/foreground Chrome and verify the latest committed state remains.
9. Repeat in Korean and Traditional Chinese for narrow mobile layout.

## Stage E — Stress / performance

Minimum P0 stress document:

- 5 or more PaperLayers
- multiple paper versions
- repeated Paint and Erase history
- zoomed viewport while editing

Pass criteria are experiential rather than a synthetic FPS number:

- no sustained input freeze
- no obvious brush/eraser lag that prevents accurate laying
- zoom/pan remains usable
- no repeated full-page flashes while active strokes move
- no layer disappears because its runtime asset failed to rehydrate
- no persistent memory-growth symptom during a normal P0 session

If a device exhibits a performance problem, record device/browser, layer count, approximate stroke count, zoom level, and the copied QA report.

## Stage F — Final novice-user acceptance

Without explaining the gestures first, ask a user to:

1. choose three papers
2. lay them in different regions
3. overlap them
4. erase the upper paper to expose the lower paper
5. Undo and Redo
6. zoom and pan
7. reload and continue from the restored artwork

P0 is accepted only when the task is understandable and the core sequence completes without a blocking defect.

## Cloudflare preview requirement

P0.9 is the first milestone where a remote HTTPS preview is operationally useful because physical iPhone and Android devices need to open the same build.

No Workers, D1, R2, account system, or cloud sync are required. A static Cloudflare Pages preview is sufficient.

Project build contract:

```text
Node: 22
Build command: npm run build
Output directory: apps/web/dist
```

After deployment, append `?qa=1` to the preview URL for device QA.
